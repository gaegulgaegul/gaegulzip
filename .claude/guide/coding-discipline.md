# Coding Discipline Guide

> 모든 개발 에이전트(node-developer, flutter-developer, react-developer)가 **구현 시점**에 따르는 판단 규칙.
> Karpathy 4원칙 + 멀티에이전트 환경 적용.

## 1. Surface Assumptions (가정 표면화)

**구현 전 반드시 수행:**

- brief.md / design-spec.md에서 모호한 부분이 있으면 **가정하지 말고 질문**
  - 먼저 자가 해결 3단계 수행 (참조: `.claude/guide/agent-communication-protocol.md`)
  - 해결 불가 시 `BLOCKED: QUESTIONS` 형식으로 반환
- 여러 해석이 가능하면 선택지를 제시: "A와 B 두 가지 해석이 가능한데, 어느 쪽인가요?"
- CTO가 없는 단독 작업이면 사용자에게 직접 질문

**Anti-pattern:**
```
❌ "아마 이렇게 하면 될 것 같다" → 자의적 해석으로 구현
✅ "이 API의 에러 응답 형식이 brief에 없습니다. { error: string } 형태로 진행할까요?" → 확인 후 구현
```

## 2. Simplicity First (최소 코드)

**자가 검증 기준:**

- "시니어 엔지니어가 이 코드를 보고 과하다고 할까?" → Yes면 단순화
- 200줄을 50줄로 줄일 수 있으면 줄일 것
- 단일 사용 추상화 금지 (3번 이상 쓰이지 않으면 인라인)
- 요청되지 않은 기능, 유연성, 설정 가능성 추가 금지

**Edge Case 처리 — 맥락별 차등 적용:**

| 맥락 | 정책 | 예시 |
|------|------|------|
| 시스템 경계 (외부 API, 사용자 입력, DB) | **적극 처리** | 잘못된 입력, 타임아웃, 인증 실패 |
| 내부 모듈 간 (함수 호출, 타입 보장) | **최소화** | 프레임워크/타입 시스템 신뢰 |
| 데이터 무결성 (DB 스키마, 비즈니스 규칙) | **적극 처리** | 유니크 제약, 필수 필드, 범위 검증 |

> 상세 기준: `.claude/guide/engineering-preferences.md` 참조

**요청에 대한 능동적 반론 (Challenge Requests):**

- 요청이 명확하더라도, 더 단순한 대안이 있으면 구현 전에 제시
- 최종 결정은 사용자가 하되, 판단에 필요한 트레이드오프 정보를 제공
- "왜 이 방식이어야 하는가?"를 한 번 더 묻는 것이 과잉 구현을 방지

```
❌ 사용자: "Redis 캐시 추가해줘" → 바로 구현 시작
✅ "현재 트래픽이면 in-memory Map으로 충분할 수 있습니다. Redis는 인프라 비용이 추가되는데, 분산 환경이나 영속성이 필요한 상황인가요?"
```

**Anti-pattern:**
```
❌ 할인 계산 하나에 Strategy 패턴 + Abstract Base Class + Config Dataclass
✅ 단일 함수로 구현. 할인 유형이 실제로 3개 이상 생기면 그때 패턴 도입
```

## 3. Surgical Changes (외과적 변경)

**변경 범위 규칙:**

- 요청과 직접 관련된 코드만 변경
- 인접 코드의 주석, 포맷팅, 네이밍 "개선" 금지
- 기존 코드 스타일과 다르더라도 맞출 것
- 기존 dead code 발견 시 언급만 하고 삭제하지 말 것

**자기 변경으로 생긴 고아 정리:**

- 자기 변경으로 unused 된 import, 변수, 함수만 정리
- 기존에 이미 unused였던 코드는 건드리지 않음

**멀티에이전트 특화 규칙:**

- work-plan.md의 "Files (생성/수정 허용)" 열에 명시된 파일만 수정
- "Files (수정 금지)" 열의 파일은 절대 수정 금지
- 다른 에이전트가 작업 중인 모듈 코드 건드리지 않음

**검증:** "모든 변경 라인이 요청에 직접 연결되는가?"

## 4. Goal-Driven Execution (검증 가능한 목표)

**모든 작업을 검증 가능한 목표로 변환:**

| 모호한 요청 | 검증 가능한 목표 |
|------------|----------------|
| "밸리데이션 추가" | "잘못된 입력에 대한 테스트 작성 → 테스트 통과시키기" |
| "버그 수정" | "버그 재현 테스트 작성 → 테스트 통과시키기" |
| "리팩토링" | "테스트 통과 확인 → 구조 변경 → 테스트 재확인" |
| "성능 개선" | "현재 응답 시간 측정 → 개선 → 재측정으로 검증" |

**스텝별 검증 체크포인트:**

```
1. [구현 스텝] → verify: [검증 명령어]
2. [구현 스텝] → verify: [검증 명령어]
```

**플랫폼별 검증 명령어:**

| 플랫폼 | 중간 검증 | 최종 검증 |
|--------|---------|---------|
| Server | `pnpm test -- [feature]` | `pnpm test && pnpm build` |
| Mobile | `flutter analyze` | `melos analyze` |
| Web | `pnpm build` + `pnpm lint` | `pnpm build && pnpm test:e2e` |

## 5. Bug Fixes: Prove It Pattern

**버그/에러 보고를 받으면 수정 전에 반드시 재현 테스트부터 작성:**

1. **Reproduce** — 버그를 재현하는 실패 테스트 작성
2. **Fix** — 테스트를 통과시키는 최소 수정 구현
3. **Confirm** — 테스트 통과로 수정 증명

**테스트 레벨 계층 — 버그를 포착할 수 있는 가장 낮은 레벨에서 재현:**

| 레벨 | 대상 | 위치 |
|------|------|------|
| Unit test | 순수 로직 버그, 격리된 함수 | 코드 옆 |
| Integration test | 컴포넌트 상호작용, API 경계 | 코드 옆 |
| UX spec test | 전체 사용자 흐름, 브라우저 의존 동작 | `apps/web/specs/` |

**환경 특이적/일시적 버그:** 테스트 작성이 불가능한 경우, 왜 불가능한지 문서화. 묵시적 생략 금지.

**Anti-pattern:**
```
❌ "에러 로그 보고 바로 코드 수정" → 재발 가능성 높음
✅ "실패 테스트 작성 → 수정 → 테스트 통과 확인" → 회귀 방지 보장
```

## 6. Context Management (컨텍스트 관리)

> 컨텍스트 윈도우는 20~40% 사용부터 품질이 저하되기 시작합니다.
> 컨텍스트를 자원처럼 관리해야 일관된 출력 품질을 유지할 수 있습니다.

**대화 범위 규칙:**

- **하나의 대화 = 하나의 기능/작업**. 인증 시스템 구현 대화에서 DB 리팩토링까지 하지 않음
- 작업이 끝나면 새 대화 시작. 이전 대화의 컨텍스트는 파일(work-plan.md, brief.md)로 전달
- 멀티스텝 작업은 각 스텝의 결과를 파일에 기록하여 대화 간 연속성 확보

**컨텍스트 복구:**

- `/compact` 후에도 품질이 안 좋으면 → `/clear` + 핵심 정보만 재입력
- 복구 우선순위: `.pdca-status.json` → 작업 문서 → `git diff` → `CLAUDE.md`
- context-recovery.sh hook이 compact 시 자동으로 핵심 상태를 복원

**Anti-pattern:**
```
❌ 한 대화에서 Plan → Design → Do → Check 전부 진행 → 컨텍스트 오염으로 후반부 품질 저하
✅ 각 PDCA 단계를 별도 대화로 실행 → 파일 기반으로 이전 결과 참조
```

## 적용 시점

이 규칙은 **Do 단계 (구현)** 에서 적용됩니다:

```
Plan → Design → [Do: 이 규칙 적용] → Check → Act → Report
                  ↑
          coding-discipline.md
```

각 개발 에이전트는 구현 시작 전 이 가이드를 읽고 준수합니다.
