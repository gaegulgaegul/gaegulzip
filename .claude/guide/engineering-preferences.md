# Engineering Preferences

> 모든 에이전트(개발자, CTO, 리뷰어)가 참조하는 엔지니어링 품질 기준.
> `coding-discipline.md`가 **구현 시점** 규칙이라면, 이 문서는 **판단 기준(가치관)**.

## 1. DRY — 반복을 공격적으로 제거

- 동일 로직이 2회 이상 등장하면 즉시 플래그
- 리뷰 시 반복 패턴을 가장 먼저 점검
- 단, 단일 사용 추상화는 금지 (Simplicity First와 균형)

**Anti-pattern:**
```
❌ 3개 모듈에서 동일한 날짜 포맷팅 로직 → 각각 인라인으로 작성
✅ formatDate() 유틸로 추출 — 변경 시 한 곳만 수정, 버그 전파 방지
```

## 2. 테스트 — 적은 것보다 많은 것이 낫다

- 테스트 없는 코드는 허용하지 않음 (Server 플랫폼)
- 엣지 케이스 테스트를 적극적으로 추가
- "이 시나리오는 안 일어나겠지"보다 "일어나면 어떻게 되지?"로 사고
- Mobile은 test-scenarios.md, Web은 Playwright E2E로 대체
- **같은 컨텍스트에서 테스트 작성**: 구현과 테스트는 같은 에이전트 세션에서 수행. 구현 컨텍스트를 가진 상태에서 테스트를 작성하면 엣지 케이스를 더 많이 발견함. 별도 세션에서 테스트만 작성하면 표면적 테스트가 됨.

**Anti-pattern:**
```
❌ "이 함수는 간단하니까 테스트 안 해도 됨" → 나중에 리팩토링 시 회귀 버그 발생
✅ 간단한 함수라도 테스트 작성 → 리팩토링 안전망 + 문서 역할
❌ 구현 에이전트와 테스트 에이전트를 분리 → 테스트가 구현 의도를 놓침
✅ 구현한 에이전트가 같은 세션에서 테스트도 작성 → 내부 로직을 아는 상태에서 엣지 케이스 포착
```

## 3. 적정 엔지니어링 — 부족하지도, 과하지도 않게

- **부족 (Under)**: 취약하고 해킹에 가까운 코드. 에러 처리 없음, 하드코딩
- **과잉 (Over)**: 불필요한 추상화, 미래 요구사항 대비 설계, 설정 가능성 남용
- **적정**: 현재 요구사항을 깔끔하게 충족. 확장 필요 시 그때 리팩토링
- 자가 검증: "시니어 엔지니어가 과하다고 할까?" + "주니어가 이해할 수 있을까?"

**Anti-pattern:**
```
❌ "인증 시스템 만들어줘" → 12개 파일, Strategy 패턴, Plugin 아키텍처
   (이유: 모호한 입력에 과잉 대응. 입력이 구체적이지 않으면 결과도 산만해짐)
✅ "기존 User 모델로 이메일/비번 인증, Redis 세션 24시간, /api/protected 미들웨어"
   → 명확한 스코프 = 적정 구현
```

## 4. Edge Case — 맥락별 차등 적용

> `coding-discipline.md`의 Simplicity First와 조화를 이루는 규칙.

| 맥락 | 정책 | 예시 |
|------|------|------|
| **시스템 경계** (외부 API, 사용자 입력, DB) | 적극 처리 | 잘못된 입력, 타임아웃, 인증 실패, rate limit |
| **내부 모듈 간** (함수 호출, 타입 보장) | 최소화 | 프레임워크 보장, TypeScript/Dart 타입 시스템 신뢰 |
| **데이터 무결성** (DB 스키마, 비즈니스 규칙) | 적극 처리 | 유니크 제약, 필수 필드, 범위 검증 |

**원칙**: 시스템 경계에서는 방어적으로, 내부에서는 타입 시스템을 신뢰하라.

**Anti-pattern:**
```
❌ 내부 함수 호출에 null 체크, try-catch, 타입 가드 남발 → 방어적 코드가 로직을 가림
✅ 외부 API 응답에만 validation + fallback → 신뢰 경계를 명확히 구분
```

## 5. 도구 선택 — Less is More

> 도구가 많을수록 에이전트가 잘못된 도구를 선택할 확률이 높아진다.

### CLI-first 원칙
- CLI가 있는 서비스를 우선 사용: `gh`, `pnpm`, `melos`, `psql`, `vercel`
- CLI는 에이전트가 직접 활용 가능하고 CLAUDE.md에 간단히 문서화하면 충분
- GUI/MCP 도구는 CLI로 대체 불가능한 경우에만 사용

### MCP 사용 범위 제한

| MCP | 허용 에이전트 | 용도 |
|-----|-------------|------|
| Serena | 모든 에이전트 | 시맨틱 코드 탐색 (grep/ripgrep 대체) |
| Playwright | `react-developer`만 | E2E 테스트 전용 |
| claude-mem | 모든 에이전트 | 크로스 세션 컨텍스트 |
| context7 | 필요 시 | 라이브러리 문서 조회 |

### 판단 기준
- "이 도구 없이 더 빠르게 할 수 있는가?" → 있으면 도구 사용하지 않음
- "도구가 컨텍스트를 보존하는가?" → 파일을 직접 읽는 게 더 빠르면 직접 읽기
- 불필요한 도구 실행은 컨텍스트 윈도우를 소비하고 에이전트 드리프트를 유발

**Anti-pattern:**
```
❌ 코드를 읽기 위해 Playwright로 브라우저를 띄움 → 느리고 컨텍스트 낭비
✅ Serena find_symbol 또는 Read로 직접 코드 읽기 → 빠르고 컨텍스트 보존
❌ 모든 에이전트에 모든 MCP 도구 부여 → 잘못된 도구 선택 빈도 증가
✅ 에이전트별 필요한 도구만 부여 → 선택지가 적을수록 정확도 향상
```

## 6. Explicit > Clever — 명시적인 코드 우선

- 암묵적 규칙보다 명시적 선언
- 매직 넘버/스트링 금지 → 상수로 추출
- 복잡한 원라이너보다 읽기 쉬운 여러 줄
- 메타프로그래밍, 과도한 제네릭 지양
- 코드를 읽는 사람이 "왜?"라고 묻지 않도록

**Anti-pattern:**
```
❌ const t = d.getTime() / 1e3 | 0;  → 무슨 의미인지 추론 필요
✅ const SESSION_EXPIRY_SEC = Math.floor(date.getTime() / 1000);  → 의도가 명확
```

## 7. Human Steering — 에이전트는 모니터링이 필요하다

> 모델은 자율적으로 작업할 수 있지만, 방향이 틀어질 수 있다. 적극적 모니터링과 재조정은 자동화할 수 없다.

- 에이전트가 드리프트하는 징후: 목표 망각, 반복 실수, 이전 결정 무시, 불필요한 작업 추가
- 자율형 실행에서도 중간 체크포인트(50% 진행 보고, 그룹 완료 시 검증)는 필수
- 문제 발생 시 "계속 시도"보다 "멈추고 사용자에게 옵션 제시"가 더 효율적
- **비용 의식**: 불필요한 도구 호출, 중복 탐색, 과도한 컨텍스트 소비를 줄여 토큰 효율 유지
